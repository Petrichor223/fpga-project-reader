# 测试、仿真与板级验证

## 先识别工程性质

找实际入口：仿真 top、UVM test/sequence、cocotb runner、Make target、CI job、仿真 Tcl/脚本、形式验证配置，或可综合的板级测试 top、ILA/VIO、串口/网络/主机测试程序。一个工程可以同时含多种入口，应分别建图。

不要把所有名含 `tb` 的文件都纳入当前仿真，也不要因没有 testbench 就断言没有测试。板级测试可能用内部 pattern generator、loopback、计数器和主机比对实现。

## 每个测试配置的说明

| 内容 | 必须确认的细节 |
|---|---|
| 入口 | 命令/脚本、工作目录、仿真器/版本、top、所选 test、seed、参数、宏、文件集、库、初始化数据和外部依赖 |
| DUT | 被测实例完整路径、有效参数/泛型、真实设计或仿真替身；多个 DUT 单独记录 |
| 时钟/复位 | 产生过程、周期计算的时间单位、相位/异步关系、释放顺序，与设计配置是否一致 |
| 激励 | driver/BFM/sequence/事务、输入模式、随机约束、配置顺序、外设模型及握手/背压 |
| 参考模型 | 行为模型、软件模型、golden 数据、预期值生成方法及其来源 |
| 比对 | monitor/scoreboard/assertion 的实际观测点、延迟匹配、容错、mask、检查使能和错误传播 |
| 结束与通过 | timeout、fatal/assert、计数器、PASS/FAIL 条件、仿真结束、脚本退出码及 CI 如何接收失败 |
| 覆盖 | 测试场景、边界/异常/复位/多时钟/背压、功能 covergroup/cover property、代码/断言覆盖的可用结果 |

追踪完整判定链：DUT 输出 → monitor/checker → error 状态 → simulation result → runner exit → CI 结果。仅有打印 `PASS`、`$finish`、成功退出或波形生成，不足以确认测试会检测功能错误；捕获异常后返回 0 的 runner 也要说明。

没有 scoreboard 时可以存在即时断言、预期输出检查或主机比对；没有参考模型时写明实际检查机制，不要求为满足格式虚构组件。

## 测试存在、运行与覆盖分开

- **测试定义**：源码实现了哪些激励与检查，是否被选定入口触发。
- **运行记录**：日志/结果是否存在、配置和输入是否匹配、何时生成、实际执行的 test/seed、通过/失败/未执行。
- **覆盖结果**：定义了 coverage 不等于收集过；有报告也需说明分母、排除项、目标阈值和配置。没有记录就填“未提供/未运行，覆盖率未知”，不能由测试数量推导覆盖率。

README 声称支持某协议，不代表已有测试覆盖其所有模式。将“代码可见覆盖的场景”“未见测试的场景”“实际量化结果”分别列出；不要把未观察到的测试直接表述为产品缺陷。

## 板级测试与形式验证

板级：说明测试 bitstream 的目标器件/板卡、接口连接、时钟来源、激励/回环路径、ILA 探针、主机命令、判定与测量条件。没有上板记录时只确认设计了哪些测试机制，不宣称硬件通过。

形式验证：记录 DUT/harness、property、assume、时钟复位约束、bound、工具/引擎、任务配置、proof/cover/counterexample 结果。一个属性证明不能扩大为整个工程正确；仅有配置文件不代表已经证明。

阅读任务默认不执行回归或上板；用户要求运行时才按现有授权和可用工具操作。缺失工具时仍输出结构、入口和未验证事项。
